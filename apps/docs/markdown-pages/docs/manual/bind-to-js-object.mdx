# Bind to JS Object

JavaScript objects are a combination of several use-cases:

- As a "record" or "struct" in other languages (like ReScript and C).
- As a hash map.
- As a class.
- As a module to import/export.

ReScript cleanly separates the binding methods for JS object based on these 4 use-cases. This page documents the first three. Binding to JS module objects is described in the [Import from/Export to JS](./import-from-export-to-js.mdx) section.

## Bind to Record-like JS Objects

### Bind Using ReScript Record

If your JavaScript object has fixed fields, then it's conceptually like a ReScript record. Since a ReScript record compiles to a clean JavaScript object, you can definitely type a JS object as a ReScript record!

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type person = {
  name: string,
  friends: array<string>,
  age: int,
}

@module("MySchool") external john: person = "john"

let johnName = john.name
```

```js
import * as MySchool from "MySchool";

let johnName = MySchool.john.name;

export { johnName };
```

</CodeTab>

External is documented [here](./external.mdx). `@module` is documented [here](./import-from-export-to-js.mdx).

If you want or need to use different field names on the ReScript and the JavaScript side, you can use the `@as` decorator:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type action = {
  @as("type") type_: string
}

let action = {type_: "ADD_USER"}
```

```js
let action = { type: "ADD_USER" };

export { action };
```

</CodeTab>

This is useful to map to JavaScript attribute names that cannot be expressed in ReScript (such as keywords).

It is also possible to map a ReScript record to a JavaScript array by passing indices to the `@as` decorator:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type t = {
  @as("0") foo: int,
  @as("1") bar: string,
}

let value = {foo: 7, bar: "baz"}
```

```js
let value = [7, "baz"];

export { value };
```

</CodeTab>

### Bind Using ReScript Object

Alternatively, you can use [ReScript object](./object.mdx) to model a JS object too:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type person = {
  "name": string,
  "friends": array<string>,
  "age": int,
}

@module("MySchool") external john: person = "john"

let johnName = john["name"]
```

```js
import * as MySchool from "MySchool";

let johnName = MySchool.john.name;

export { johnName };
```

</CodeTab>

### Bind Using Special Getter and Setter Attributes

Alternatively, you can use `get` and `set` to bind to individual fields of a JS object:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type textarea
@set external setName: (textarea, string) => unit = "name"
@get external getName: textarea => string = "name"
```

```js
/* This output is empty. Its source's type definitions, externals and/or unused code got optimized away. */
```

</CodeTab>

You can also use `get_index` and `set_index` to access a dynamic property or an index:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type t
@new external create: int => t = "Int32Array"
@get_index external get: (t, int) => int = ""
@set_index external set: (t, int, int) => unit = ""

let i32arr = create(3)
i32arr->set(0, 42)
Console.log(i32arr->get(0))
```

```js
let i32arr = new Int32Array(3);

i32arr[0] = 42;

console.log(i32arr[0]);

export { i32arr };
```

</CodeTab>

## Bind to Hash Map-like JS Object

If your JavaScript object:

- might or might not add/remove keys
- contains only values that are of the same type

Then it's not really an object, it's a hash map. Use [Dict](/docs/manual/api/stdlib/dict), which contains operations like `get`, `set`, etc. and cleanly compiles to a JavaScript object still.

## Bind to a JS Object That's a Class

Use `new` to emulate e.g. `new Date()`:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type t
@new external createDate: unit => t = "Date"

let date = createDate()
```

```js
let date = new Date();

export { date };
```

</CodeTab>

You can chain `new` and `module` if the JS module you're importing is itself a class:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
type t
@new @module external book: unit => t = "Book"
let myBook = book()
```

```js
import * as Book from "Book";

let myBook = new Book();

export { myBook };
```

</CodeTab>

### Represent Class Inheritance

ReScript does not define classes, but bindings can describe the inheritance relationships between existing JavaScript classes. Give each class its own type, then use a **private type abbreviation** to relate a subclass to its parent.

For example, suppose a JavaScript module exports these classes:

```js
// animals.js
export class Animal {
  constructor(name) {
    this.name = name;
  }

  getName() {
    return this.name;
  }
}

export class Mammal extends Animal {}

export class Dog extends Mammal {
  bark() {
    return "Woof!";
  }
}
```

The hierarchy is `Animal → Mammal → Dog`. Start with an abstract type for `Animal` and bind its methods with [`@send`](./bind-to-js-function.mdx#object-method):

```res file=Animal.res
type t

@send external getName: t => string = "getName"
```

In `Mammal.res`, declare that a mammal can be used as an animal:

```res file=Mammal.res
type t = private Animal.t
```

Repeat the pattern for `Dog`, and bind its constructor and methods:

```res file=Dog.res
type t = private Mammal.t

@new @module("./animals.js") external make: string => t = "Dog"
@send external bark: t => string = "bark"
```

The constructor still returns `Dog.t`. The private abbreviations let you explicitly **coerce** that value to its parent types with `:>`:

<CodeTab labels={["ReScript", "JS Output"]}>

```res
let dog = Dog.make("Rex")
let mammal = (dog :> Mammal.t)
let animal = (dog :> Animal.t)

let name = animal->Animal.getName
let sound = dog->Dog.bark
```

```js
import * as Dog from "./Dog.js";

let dog = Dog.make("Rex");

let name = dog.getName();

let sound = dog.bark();

let mammal = dog;

let animal = dog;

export { dog, mammal, animal, name, sound };
```

</CodeTab>

Coercion works through the hierarchy, so `Dog.t` can be coerced directly to `Animal.t` without first being assigned to a `Mammal.t` variable. To call an inherited method without keeping another variable, write:

```res
let name = (Dog.make("Rex") :> Animal.t)->Animal.getName
```

The coercion changes only the type used by the compiler. It does not wrap or copy the instance, call a constructor, or change JavaScript's method dispatch. The generated `mammal` and `animal` variables refer to the same JavaScript object as `dog`.

#### Why Use `private`?

A regular [type alias](./type.mdx#type-alias), such as `type t = Animal.t`, would make the types interchangeable. `type t = private Animal.t` keeps the subclass distinct while permitting coercion to the parent.

The compiler requires `:>` when passing a subclass instance to a binding that expects the parent type. A type annotation with `:` does not perform that coercion.

The reverse conversion is rejected: an arbitrary `Animal.t` cannot be coerced to `Dog.t`, because not every animal is a dog. After a value has been viewed as `Animal.t`, dog-specific methods also require the original `Dog.t` value. Keep that value if you need both APIs.

These declarations describe an existing JavaScript relationship; they do not create inheritance or check instances at runtime. Only declare a private abbreviation when the JavaScript API guarantees that the subclass can be used as its parent.

#### Keep the Relationship Visible in Interfaces

If your binding has a [`.resi` interface](./module.mdx#signatures), expose the private abbreviation there too. For example, `Mammal.resi` should contain:

```res file=Mammal.resi
type t = private Animal.t
```

Exposing only `type t` would hide the relationship from callers, preventing them from coercing `Mammal.t` to `Animal.t`.

The same approach works for larger libraries. In [OpenLayers](https://openlayers.org/en/latest/apidoc/module-ol_source_Tile-TileSource.html), for example, `TileSource.t` can be declared as `private Source.t`. Bindings for descendants such as [WMTS](https://openlayers.org/en/latest/apidoc/module-ol_source_WMTS-WMTS.html) can expose the relationship to `TileSource.t` without binding every intermediate class.
