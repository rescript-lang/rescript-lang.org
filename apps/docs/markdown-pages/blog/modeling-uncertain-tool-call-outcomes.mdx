You start a documentation lookup, then start another run before the first reply arrives. The second run finds the Promise page first. How should the UI handle an older answer arriving afterward?

Assigning every arriving answer to the result field would put the older answer under the newer request. A local deadline needs different handling too: with no final reply, the UI can't say that the tool rejected the call.

We'll describe what the UI knows with ReScript v12 variants and connect the model to ordinary browser controls. You'll choose when to release replies and local deadline observations from a manually held queue. You don't need a model account or remote tool.

## Model a call with variants

A call can be:

- `Pending`: waiting for a final reply.
- `Completed(output)`: received an explicit completion with a string result.
- `Rejected(reason)`: received an explicit rejection with a string reason.
- `Unresolved`: observed a local deadline without receiving a final reply.

`Unresolved` can still become `Completed` or `Rejected`. Passing a deadline tells the client that it's still missing a final reply. It doesn't tell us whether the tool stopped, failed, or continued working.

A [variant](../docs/manual/variant.mdx) keeps the payload with the state that gives it meaning. A completed empty string is still a completion. We won't use the presence of result text to decide which state we're in.

For one matching call identity, use these transitions:

| Current state         | Incoming event                    | Next state        |
| --------------------- | --------------------------------- | ----------------- |
| Pending               | Completion                        | Completed(output) |
| Pending               | Explicit rejection                | Rejected(reason)  |
| Pending               | Local deadline                    | Unresolved        |
| Unresolved            | Completion                        | Completed(output) |
| Unresolved            | Explicit rejection                | Rejected(reason)  |
| Unresolved            | Local deadline                    | Unresolved        |
| Completed or Rejected | Any later final reply or deadline | Unchanged         |

The first accepted final reply wins. This policy makes duplicate delivery predictable, including a contradictory later reply. The client reports that it ignored the later final; it doesn't establish which reply reflects the tool's authoritative outcome.

## Match both identifiers

Use a pair: `runId` identifies the run, and `callId` identifies a call within it. Every run in this lab uses the same `callId`, `lookup`, so checking that field alone would accept an older run's reply. Both fields must match exactly.

Deadlines need the same guard. A deadline captured for run-1 must not turn run-2 into `Unresolved`. Starting a new run creates a new pending call, while older messages stay in the queue so we can exercise that boundary.

These identifiers correlate messages. They don't authenticate a sender. In a real application, the transport must establish who can send replies.

## Add the model

Create `src/ToolCall.res`. JavaScript will keep its `call` value opaque and use `begin`, `receive`, `expire`, and `view`.

```res file=ToolCall.res
type key = {runId: string, callId: string}

type status =
  | Pending
  | Completed(string)
  | Rejected(string)
  | Unresolved

type call = {key: key, status: status}
type reply = {key: key, outcome: result<string, string>}
type update = {call: call, notice: string}

type view = {
  runId: string,
  callId: string,
  status: string,
  detail: string,
}

let begin = (runId, callId): call => {key: {runId, callId}, status: Pending}

let sameKey = (a: key, b: key) => a.runId === b.runId && a.callId === b.callId

let decode = (json: JSON.t): result<reply, string> => {
  open JSON
  switch json {
  | Object(dict{
      "runId": String(runId),
      "callId": String(callId),
      "kind": String("completed"),
      "output": String(output),
    }) =>
    Ok({key: {runId, callId}, outcome: Ok(output)})
  | Object(dict{
      "runId": String(runId),
      "callId": String(callId),
      "kind": String("rejected"),
      "reason": String(reason),
    }) =>
    Ok({key: {runId, callId}, outcome: Error(reason)})
  | _ =>
    Error("Invalid reply: expected string identifiers and a completed output or rejected reason.")
  }
}

let parse = raw => {
  let parsed = try {
    Ok(JSON.parseOrThrow(raw))
  } catch {
  | _ => Error("Invalid JSON: could not parse message.")
  }
  switch parsed {
  | Ok(json) => decode(json)
  | Error(message) => Error(message)
  }
}

let accept = (call: call, reply: reply): update => {
  if !sameKey(call.key, reply.key) {
    {call, notice: "Ignored reply: different call identity."}
  } else {
    switch call.status {
    | Completed(_) | Rejected(_) => {call, notice: "Ignored reply: final outcome already recorded."}
    | Pending | Unresolved =>
      switch reply.outcome {
      | Ok(output) => {
          call: {...call, status: Completed(output)},
          notice: "Accepted completion.",
        }
      | Error(reason) => {
          call: {...call, status: Rejected(reason)},
          notice: "Accepted rejection.",
        }
      }
    }
  }
}

let receive = (call, raw): update =>
  switch parse(raw) {
  | Ok(reply) => accept(call, reply)
  | Error(notice) => {call, notice}
  }

let expire = (call: call, runId, callId): update => {
  if !sameKey(call.key, {runId, callId}) {
    {call, notice: "Ignored deadline: different call identity."}
  } else {
    switch call.status {
    | Pending => {
        call: {...call, status: Unresolved},
        notice: "Unresolved: deadline observed without a final reply.",
      }
    | Unresolved => {call, notice: "Still unresolved: no final reply."}
    | Completed(_) | Rejected(_) => {
        call,
        notice: "Ignored deadline: final outcome already recorded.",
      }
    }
  }
}

let view = (call: call): view => {
  let (status, detail) = switch call.status {
  | Pending => ("Pending", "")
  | Completed(output) => ("Completed", output)
  | Rejected(reason) => ("Rejected", reason)
  | Unresolved => (
      "Unresolved",
      "No final reply observed. A matching late reply can still resolve this call.",
    )
  }
  {runId: call.key.runId, callId: call.key.callId, status, detail}
}
```

Follow a reply through `receive`. [`JSON.parseOrThrow`](/docs/manual/api/stdlib/json/) first parses the string into `JSON.t`; the catch covers parsing only. `decode` checks the object fields and the string payload selected by `kind`. As the [JSON manual](../docs/manual/json.mdx) explains, giving parsed JSON a desired type doesn't validate its shape.

Invalid JSON and valid JSON with the wrong shape produce different diagnostics. Neither becomes a tool rejection. Missing fields, non-string identifiers or payloads, arrays, primitives, and unknown kinds leave the current call unchanged.

Extra object fields are allowed and ignored. Empty strings are valid strings, including identifiers; there is no trimming or coercion. An application that prohibits empty identifiers should add that rule at this boundary.

Once the reply is decoded, `accept` checks both identifiers and applies the transition table. A later final reply reaches the terminal-state branch and leaves the first result intact. `expire` preserves that result too. When a state changes, the update constructs a new record and leaves the caller's previous value intact.

`view` handles all four constructors explicitly. The browser doesn't need to inspect generated variant tags or repeat the presentation switch in JavaScript. The earlier [Improving interop](./improving-interop.mdx) article explores variants at JavaScript boundaries; its v11 examples are historical context. This example uses v12's `JSON.t` and dictionary patterns.

### src/main.js

```js
import * as ToolCall from "./ToolCall.res.js";

const byId = (id) => document.getElementById(id);
let runNumber = 1;
let messageNumber = 0;
let current = ToolCall.begin("run-1", "lookup");

function render(notice) {
  const shown = ToolCall.view(current);
  byId("run-id").textContent = shown.runId;
  byId("call-id").textContent = shown.callId;
  byId("status").textContent = shown.status;
  byId("detail").textContent = shown.detail;
  byId("notice").textContent = notice;
}

function fillReply() {
  const shown = ToolCall.view(current);
  byId("reply").value = JSON.stringify({
    runId: shown.runId,
    callId: shown.callId,
    kind: "completed",
    output: `Answer for ${shown.runId}`,
  });
}

function queueMessage(label, apply) {
  const number = ++messageNumber;
  const row = document.createElement("li");
  const description = document.createElement("p");
  description.textContent = `Message ${number}: ${label}`;
  const button = document.createElement("button");
  button.type = "button";
  button.textContent = `Deliver message ${number}`;
  button.dataset.messageId = String(number);
  button.addEventListener("click", () => {
    queueMicrotask(() => {
      const update = apply(current);
      current = update.call;
      render(update.notice);
      const receipt = document.createElement("li");
      receipt.textContent = `Delivered message ${number}: ${update.notice}`;
      byId("receipts").append(receipt);
    });
  });
  row.append(description, button);
  byId("queue").append(row);
}

byId("start").addEventListener("click", () => {
  current = ToolCall.begin(`run-${++runNumber}`, "lookup");
  fillReply();
  render("Started a new run. Older messages remain queued.");
});

byId("queue-reply").addEventListener("click", () => {
  const raw = byId("reply").value;
  queueMessage(raw, (call) => ToolCall.receive(call, raw));
});

byId("queue-deadline").addEventListener("click", () => {
  const { runId, callId } = ToolCall.view(current);
  queueMessage(`Deadline for ${runId}/${callId}`, (call) =>
    ToolCall.expire(call, runId, callId),
  );
});

fillReply();
render("Ready. Queue a reply or a local deadline observation.");
```

The browser keeps one current call and renders it through `view`. The host queues deliveries and writes output with `textContent`, so even text that looks like HTML stays literal. An ignored stale reply appears in the receipts while the current result stays on screen; the result and transition notice have separate fields.

Queueing a reply captures the textarea's current string. Editing the textarea afterward cannot change that message. A queued deadline captures both identifiers. Each delivery callback applies its captured event to the call that is current at delivery time.

The queue is in process, with no Web Worker, network request, or timer. Holding a message supplies the controllable delay. [`queueMicrotask`](https://developer.mozilla.org/en-US/docs/Web/API/Window/queueMicrotask) delivers it asynchronously after the click handler finishes; a microtask isn't a timed delay. Deliver buttons stay enabled so the same entry can arrive more than once.

## Try delayed and reordered replies

Use the page controls in this order. The run counter starts again at run-1 when you reload the lab.

1. Leave run-1's identity in the textarea, change `output` to `Old answer`, and choose **Queue reply**. Leave that message held. The status stays `Pending`.
2. Choose **Start new run**. The page shows run-2/lookup and a fresh `Pending` state. Change its output to `New answer`, queue it, and deliver message 2. The state becomes `Completed` with `New answer`.
3. Deliver message 1. A receipt reports a different call identity. The page still shows run-2, `Completed`, and `New answer`.
4. Deliver message 2 again. Then queue another run-2 completion with different output and deliver it. Both notices report that a final outcome is already recorded. Try an opposite-kind reply by changing `kind` to `rejected` and replacing `output` with a string `reason`. That also preserves `New answer`.
5. Start a new run. Queue its deadline, then queue its default completion. Deliver the deadline first. Read the `Unresolved` status and uncertainty text, then deliver the completion. It becomes `Completed`.
6. Start another run and repeat the deadline exercise with `kind: "rejected"` and `reason: "The query is empty"`. Only delivery of that explicit reply changes `Unresolved` to `Rejected`.
7. In a fresh run, deliver a completion before its queued deadline. The deadline cannot erase the result. Next, queue a deadline, start another run, and deliver the old deadline. The new call stays `Pending`.
8. While pending, queue a completion with the current `runId` but another `callId`. Deliver it and check that nothing changes. Try `{` as the whole reply, then valid JSON with a numeric `output`. Each produces a diagnostic while preserving the call.
9. In a fresh run, complete with an empty output string. The status still says `Completed`. In another run, use markup-looking output such as `<strong>Found it</strong>`. The result shows the angle brackets and tags as text.

You can use the JSON input and native buttons from the keyboard too. The receipt list records arrival order. It doesn't show that a remote operation ran. Repeating a deadline while unresolved leaves the state unresolved.

## What the compiler checks

[Pattern matching](../docs/manual/pattern-matching-destructuring.mdx) lets the compiler check that `view` handles this closed set of statuses. Remove the `Rejected` arm and a strict build rejects the missing case. Add a constructor such as `Cancelled` and each match that needs to handle it must change too. Keep the warning-as-error flags in the build command so missing cases stop the build.

Exhaustiveness says something about the typed values reaching those matches. It doesn't validate an arbitrary JSON string, prove that identifiers belong together, or enforce the first-final policy by itself. The decoder and transition guards do that work at runtime. Similarly, JavaScript consumers must respect the module boundary; keeping `call` opaque here is a host convention, not a runtime access restriction.

A [promise](../docs/manual/promise.mdx) settles once. This lab deliberately accepts multiple delivered messages, so a promise's settlement alone can't express its protocol. An [async function](../docs/manual/async-await.mdx) could receive messages from a real transport, but it would still need validation and correlation. Racing a reply against a deadline and discarding the losing reply would also discard the late resolution we chose to preserve.

## Use the model with a real transport

The model follows one currently displayed call. A real integration still needs tool execution, authenticated transport, accurate deadline scheduling, cancellation, retries and persistence; this lab implements none of those. Accepting a reply once in the UI also doesn't guarantee exactly-once tool execution.

Pass the transport's reply strings to `receive`, pass each deadline's captured identifiers to `expire`, and render the current call through `view`. The UI accepts the first valid final reply whose two identifiers match. Until then, a deadline leaves the call unresolved so a matching late reply can still resolve it.
